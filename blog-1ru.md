# Кейс: Discord VoIP Протокол & State Poisoning

## 🎯 Краткий обзор (60 секунд)

**Что случилось:** Уязвимость в системе голосовых звонков Discord позволяла атакующим селективно мутить конкретных пользователей без их ведома, используя эксплойт координации "кто говорит".

**Реальное влияние:** Представь, что ты на стриме или в рейд-колле - внезапно твоя команда не слышит тебя, но ты видишь себя "говорящим" как обычно. Никаких ошибок, никаких индикаторов что что-то не так.

**Уровень риска:** Средняя серьёзность. Требует технических знаний и нахождения в том же голосовом канале. Не может украсть учётные данные или шпионить за разговорами.

**Статус:** Discord фиксит это через систему шифрования DAVE. Полный патч обязателен с 1 марта 2026 года.

**Техническое название:** SSRC Spoofing via Signaling Plane Injection

---

## 📖 Понимание основ

### Как на самом деле работает голос в Discord

Представь голосовые звонки Discord как сложную систему доставки почты с двумя отдельными отделами:

**1. Центр управления (Signaling Plane)**
- Отслеживает кто сейчас говорит
- Назначает каждому человеку уникальный ID номер (SSRC)
- Координирует тайминг доставки голоса
- Использует WebSocket протокол для мгновенных обновлений

**2. Сеть доставки (Media Plane)**
- Несёт твои реальные голосовые/видео данные
- Зашифрованные end-to-end пакеты
- Использует UDP протокол для скорости
- Не знает КТО ты, только твой ID номер

**Уязвимость:** Атакующий мог обмануть Центр управления, заставив его назначить твои голосовые пакеты на неправильный маршрут доставки, эффективно замутив тебя, при этом выглядя так, будто всё работает нормально.

### Что делает это возможным?

Проблема возникает из-за **предположений о доверии** в legacy системе:
- Центр управления транслирует SSRC назначения всем в канале
- Он доверяет клиентским отчётам о состоянии говорения без криптографической проверки
- Есть короткое окно (2-14ms), где обновления состояния могут быть внедрены

## Краткая сводка

**Уязвимость:** SSRC Spoofing via Signaling Plane Injection

**Вектор атаки:** Манипуляция WebSocket Opcode 5 (Speaking State)

**Воздействие:** Селективный audio DoS, рассинхронизация состояния говорения

**Затронуто:** Legacy Discord голосовые ноды (до-DAVE)

**Таймлайн:** Эксплуатируемо до 1 марта 2026 (сценарии даунгрейда)

**Митигация:** DAVE E2EE протокол (Op 21-31 криптографическая привязка)

## 🔬 Технический Deep-Dive

### Ключевая терминология

Прежде чем погружаться в методологию, важно определить основные технические компоненты Discord VoIP архитектуры:

**Основные концепции:**
- **SSRC (Synchronization Source)**: Уникальный 32-битный идентификатор, который связывает медиа-потоки с конкретными пользователями в инфраструктуре Discord.
  - *Простая аналогия:* "Обратный адрес" твоего голосового пакета
  
- **Signaling Plane**: WebSocket-основанный слой управления (Gateway), используемый для оркестрации протокола, аутентификации и управления состоянием.
  - *Простая аналогия:* Диспетчерская вышка, координирующая голосовые данные
  
- **Media Plane**: UDP-основанный слой (SRTP), который несёт реальные зашифрованные голосовые и видео данные.
  - *Простая аналогия:* Самолёт, несущий твой реальный голос
  
- **Opcode**: Идентификаторы на уровне протокола (например, Op 5, Op 2), которые триггерят специфические действия в Signaling Plane.
  - *Простая аналогия:* Коды команд типа "/mute" или "/unmute"

**Протоколы безопасности:**
- **DAVE**: Новый протокол End-to-End шифрования Discord, который обеспечивает криптографическую привязку между сигнальными идентичностями и медиа-потоками.
  - *Цель:* Предотвращает именно тот эксплойт, описанный в этом исследовании
  
- **MLS (Messaging Layer Security)**: IETF стандарт для группового шифрования, используемый DAVE для обеспечения forward secrecy и post-compromise security.
  - *Цель:* Гарантирует, что даже если одна сессия скомпрометирована, прошлые/будущие сессии остаются безопасными

---

### Архитектура: Разделение плоскостей

VoIP инфраструктура Discord работает на двух отдельных плоскостях:

**1. Signaling Plane (WebSocket):** Обрабатывает оркестрацию (Opcodes 0, 2, 5, 8). Здесь сервер отслеживает состояния говорения и **SSRC** (Synchronization Source Identifier) маппинг.

**2. Media Plane (UDP/SRTP):** Несёт реальные зашифрованные голосовые/видео данные.

**Критическое проектное решение:** Эти плоскости работают независимо по причинам производительности. Media Plane доверяет SSRC назначениям от Signaling Plane без повторной верификации. Этот архитектурный выбор делает атаку возможной.

---

### Этап 1: Gateway Handshake

Поток строго последовательный в Voice Gateway. Как зафиксировано в наших логах живой сессии:

- **Op 0 (Identify):** Начальный хэндшейк аутентификации.
- **Op 8 (Hello):** Синхронизация интервала heartbeat (13750ms).
- **Op 2 (Ready):** Утечка координат медиа-ноды, раскрывающая внутренний IP и Port сервера.

**Последствия для безопасности:** Ready событие сливает детали внутренней инфраструктуры, которые помогают в разработке эксплойта.

---

### Этап 2: Identity Mapping (Утечка SSRC)

Фундаментальный архитектурный недостаток протокола - **Speaking Broadcast**. Когда участник активирует свой аудио, сервер отправляет Opcode 5 всем членам канала.

**SSRC** (Synchronization Source Identifier) - уникальный 32-битный идентификатор, назначаемый каждому участнику VoIP сессии. Он служит внутренним токеном маршрутизации, который связывает медиа-потоки с конкретными пользователями в инфраструктуре Discord.

![Утечка SSRC, захваченная из живого лога трафика](ssrc-leaks.jpg)

#### Визуализация потока данных

```text
[ Атакующий ]        [ Discord Gateway ]        [ Целевой пользователь ]
      |                    |                              |
      |---(Sniff Op 5)---->|                              |
      |                    |<---(SSRC Broadcast)----------|
      |                    |                              |
      |---(Forge Op 5)---->|                              |
      |   (Target SSRC)    |                              |
      |                    |---(State Poisoning)--------->|
      |                    |   (Collision / DoS)          |
```

Как показано, атакующий получает внутренний идентификатор сессии цели (SSRC) из легитимного сигнального трафика и затем внедряет конфликтующее обновление состояния обратно в Gateway.

**Что испытывает жертва:**
- Их Discord клиент показывает их как "говорящих" (зелёное кольцо активно)
- Другие пользователи вообще их не слышат
- Никаких сообщений об ошибках или предупреждений
- Переподключение не фиксит проблему (атакующий может заново внедрить)

---

### Этап 3: Эксплойт - Signaling State Poisoning

Уязвимость заключается в **рассинхронизации состояния** между плоскостями управления и медиа.

#### 1. Анализ задержки broadcast в 14ms

Как зафиксировано в нашей телеметрии, сервер использует асинхронный механизм broadcast для состояний говорения. В рамках одного **14-миллисекундного окна**, сервер отправил 4 отдельных **Opcode 5** пакета:

```json
03:09:40.318 -> SSRC: 5322
03:09:40.327 -> SSRC: 5145 (+9ms)
03:09:40.329 -> SSRC: 5319 (+11ms)
03:09:40.330 -> SSRC: 5039 (+12ms)
```

**Находка:** Эта скорость предполагает архитектуру "Fire and Forget" broadcast. Сервер приоритизирует быструю сигнализацию клиентам над строгой, атомарной валидацией привязки сессия-к-SSRC.

**Окно атаки:** Задержка 2-14ms между обновлениями состояния создаёт возможность для инъекции до того, как сервер сможет проверить консистентность.

#### 2. SSRC Collision Injection (L7)

Перехватив SSRC цели через broadcast, атакующий может создать поддельный **Opcode 5** payload. Поскольку payload клиент-к-серверу исключает user_id, он полагается исключительно на **ssrc** для обновлений состояния. Внедрение этого в сигнальный поток отравляет таблицу маршрутизации медиа-сервера, вызывая полную рассинхронизацию пакетов (тишину) для жертвы.

**Структура технического payload:**
```json
{
  "op": 5,
  "d": {
    "speaking": 1,
    "delay": 0,
    "ssrc": 0xTARGET_SSRC  // Идентификатор жертвы
  }
}
```

**Почему это работает:**
- Нет криптографической подписи на Op 5 в legacy нодах
- Сервер доверяет SSRC без верификации идентичности отправителя
- Media plane слепо следует маршрутизации signaling plane

### Экспериментальная валидация: Контролируемая среда

Для валидации этого архитектурного недостатка мы использовали **Local Browser Proxy Hook** (MITM на нашей собственной клиентской сессии).

**Установка:**
1. Два контролируемых аккаунта в выделенном sandbox голосовом канале
2. Browser DevTools WebSocket перехват на Аккаунте A
3. Инструменты захвата и анализа пакетов

**Выполнение:**
1. Аккаунт A внедрил модифицированный Op 5 payload с SSRC цели ([REDACTED_SSRC])
2. Payload был принят Discord Gateway без валидации
3. Таблица маршрутизации медиа-сервера была отравлена

**Результаты:**
- **Signaling Layer:** Видимая рассинхронизация состояния "Speaking"
- **Media Layer:** Индуцированная audio коллизия/подавление для целевого аккаунта
- **Client UI:** Цель показывалась как "говорящая", но аудио отбрасывалось

**Вывод:** Эксплойт успешно отравляет сигнальное состояние в локальном sandbox, подтверждая уязвимость на Legacy нодах до мандата **DAVE** (Discord Audio/Video Encryption) v1.

| Компонент | Статус | Эмпирическое доказательство |
| :--- | :--- | :--- |
| Клиентский SSRC контроль | ✅ Подтвержденно | Клиент-к-Серверу Op 5 Payload |
| Быстрый Broadcast (2-14ms) | ✅ Подтвержденно | Асинхронный анализ логов |

- **Персистентность:** Повторно применяемо пока цель не покинет канал
- **Обнаружение:** Очень сложно - выглядит как проблема сети/клиента
- **Область воздействия:** Таргетинг по пользователю, нет массового нарушения

### Этический протокол: Ответственное раскрытие

Это исследование было проведено в локальной контролируемой среде специально для изучения безопасности RTC протокола.

**Этика исследования:**
- **Методология:** Перехват был ограничен локальными browser memory hooks на собственных аккаунтах
- **Масштаб:** Только тестирование в sandbox, никакой production эксплуатации
- **Отчётность:** Находки касательно "Downgrade Window" и Plane Separation были синтезированы для осведомлённости о безопасности
- **Таймлайн:** Discord был проинформирован до публичного раскрытия

**Статус митигации:** По состоянию на 2024-2025, Discord активно нейтрализует этот вектор через **DAVE** (Discord Audio/Video Encryption) протокол, который реализует End-to-End Encryption (E2EE) для голосовых и видео коммуникаций.

---

## 🛡️ Защита Deep-Dive: Почему DAVE убил эксплойт

DAVE протокол Discord вводит **Zero Trust Signaling**. В Legacy нодах сервер слепо доверял WebSocket (Signaling Plane). В DAVE-включённых нодах сервер обеспечивает криптографическую привязку между SSRC и **MLS Session Key** (Messaging Layer Security Session Key).

**Фундаментальный сдвиг:**
- **Legacy:** "Если ты говоришь что ты Пользователь X, я направлю твои пакеты на SSRC Пользователя X"
- **DAVE:** "Докажи что ты Пользователь X криптографической подписью, или я отброшу твои пакеты"

MLS - это IETF стандарт для группового шифрования сообщений, который обеспечивает forward secrecy и post-compromise security.

### Новая протокольная защита (Opcodes 21-31)

Переход на E2EE ввёл набор новых валидационных Opcodes:

| Op | Название | Цель |
| :--- | :--- | :--- |
| 21-22 | transition | Выполнить/Подготовить E2EE эпоху |
| 26 | mls_key_package | Ядро валидации: Привязывает SSRC к Crypto Key |
| 27-28 | mls_proposals | Обмен верификацией идентичности |

**Как это предотвращает эксплойт:**
1. Каждое обновление состояния говорения должно включать криптографическую подпись
2. Подпись верифицируется против MLS session key пользователя
3. SSRC криптографически привязан к аутентифицированной идентичности
4. Поддельные Op 5 пакеты отклоняются на уровне Gateway

---

### Оставшийся вектор: Protocol Downgrades

Наше исследование выявило критический "fail-open" механизм:

**Сценарий:** Если хотя бы один участник в звонке использует клиент, который не поддерживает DAVE v1, медиа-нода выполняет **Protocol Downgrade** к Legacy.

**Воздействие:** В состоянии даунгрейда криптографическая валидация SSRC-к-Key отключена, повторно включая уязвимость **Signaling State Poisoning**.

**Реальные триггеры даунгрейда:**
- Устаревшие версии Discord клиента
- Мобильные клиенты на медленных циклах обновления
- Боты, использующие legacy voice gateway APIs
- Пользователи, отключившие автообновления

**Последствия для безопасности:** Один legacy клиент компрометирует модель безопасности всего канала до марта 2026.

---

### Дорожная карта перехода: 1 марта 2026

Этот эксплойт работает в определённом **Downgrade Window**. Согласно внутренней дорожной карте Discord, фаза "Legacy Support" имеет жёсткую дату истечения: **1 марта 2026**.

**Таймлайн:**
- **2024:** Разработка и тестирование DAVE протокола
- **2025:** Постепенный rollout DAVE на все клиенты
- **1 марта 2026:** Поддержка legacy протокола отключена навсегда
- **После марта 2026:** Эксплойт больше не функционален

После этой даты все голосовые подключения будут требовать поддержку DAVE, полностью устраняя вектор даунгрейда.

## ❓ Часто задаваемые вопросы

**В: Я в опасности прямо сейчас?**  
О: Минимальный риск для большинства пользователей. Эксплойт требует технических знаний WebSocket и нахождения в том же голосовом канале что и жертва. Discord активно внедряет DAVE защиту.

**В: Могут ли взломать мой аккаунт этим?**  
О: Нет. Эта уязвимость позволяет только audio DoS (селективный мут). Она не может:
- Украсть учётные данные аккаунта
- Получить доступ к личным сообщениям
- Шпионить за разговорами
- Эскалироваться к другим атакам

**В: Как понять что кто-то использовал это на мне?**  
О: Ты бы видел себя как "говорящего" (зелёное кольцо вокруг аватара), но никто в канале не слышит тебя. Переподключение не фиксит это, если атакующий персистит.

**В: Это затрагивает личку или только серверы?**  
О: Любой голосовой канал - прямые звонки, групповые DM, и серверные голосовые каналы.

**В: А как насчёт видео звонков?**  
О: В основном затрагивает аудио, но похожие принципы сигнализации применяются к видео потокам (хотя видео имеет дополнительные слои валидации).

**В: Мне стоит перестать использовать Discord голос?**  
О: Нет. Риск низкий, и Discord активно патчит это. Держи свой клиент обновлённым.

**В: Что мне нужно сделать для защиты?**  
О: Просто держи Discord авто-обновления включёнными (настройка по умолчанию). После 1 марта 2026 это полностью запатчено.

**В: Можно ли использовать это для массового грифинга?**  
О: Нет. Это таргетированная атака, требующая идентификации SSRC на каждую жертву. Не практично для массового нарушения.

**В: Почему эта уязвимость существовала?**  
О: Это legacy проектное решение, приоритизирующее производительность (быстрая сигнализация) над безопасностью. DAVE фиксит это современной криптографической верификацией.

## 📊 Оценка воздействия

### Реальные сценарии атаки

**Сценарий 1: Соревновательный гейминг**
- Атакующий присоединяется к войсу в рейтинговой игре
- Мутит шоткола команды в критический момент
- Команда теряет координацию, матч проигран
- **Воздействие:** Высокая фрустрация, конкурентный дизадвантаж

**Сценарий 2: Live Streaming**
- Стример в Discord звонке со зрителями
- Атакующий мутит стримера mid-stream
- Стрим кажется сломанным, зрители уходят
- **Воздействие:** Урон репутации, потеря зрителей

**Сценарий 3: Онлайн классы/митинги**
- Атакующий присоединяется к образовательному голосовому каналу
- Селективно мутит учителя или презентера
- Класс/митинг нарушен
- **Воздействие:** Образовательное/бизнес нарушение

### Что это НЕ МОЖЕТ делать

❌ Красть пароли или токены аккаунтов  
❌ Получать доступ к личным сообщениям или DM  
❌ Записывать или шпионить за разговорами  
❌ Распространяться на других пользователей автоматически  
❌ Работать без нахождения в том же канале  
❌ Персиститься после того как атакующий ушёл

## 🎓 Технические выводы

**Для исследователей безопасности:**
1. Разделение плоскостей в VoIP требует криптографической привязки
2. "Fire and forget" архитектуры создают окна race condition
3. Broadcast-основанная синхронизация состояния уязвима без аутентификации
4. Legacy совместимость может подорвать современные функции безопасности

**Для разработчиков:**
1. Никогда не доверяй клиентским идентификаторам без верификации
2. Криптографическая привязка между плоскостями управления и данных обязательна
3. Fail-secure, не fail-open, во время протокольных переходов
4. Оптимизации производительности не должны компрометировать основы безопасности

**Для проектировщиков протоколов:**
1. Zero-trust принципы применяются к внутренней сигнализации, не только внешним APIs
2. Синхронизация состояния требует атомарных, аутентифицированных операций
3. Downgrade атаки реальны - планируйте таймлайны устаревания тщательно
4. E2EE обеспечивает больше чем приватность - оно предотвращает спуфинг идентичности

## Финальное заключение

Угроза "Signaling State Poisoning" представляет значимый кейс-стади в современной VoIP безопасности. Хотя Discord движется к обязательной E2EE среде к 1 марта 2026, текущая фаза перехода подчёркивает вечную борьбу между обратной совместимостью и zero-trust верификацией.

**Ключевые уроки:**
- Поддержка legacy протокола создаёт эксплуатируемые окна
- Оптимизация производительности не может компрометировать основы безопасности
- Криптографическая привязка идентичности обязательна для современного VoIP
- Ответственное раскрытие и постепенная миграция защищают пользователей во время переходов

**Таймлайн раскрытия:**
- Уязвимость обнаружена и валидирована в контролируемой среде
- Discord проинформирован до публикации
- Публичное раскрытие после начала DAVE rollout
- Полный таймлайн митигации: 1 марта 2026
